## 1. Executive Summary

리그·구장 주최자가 용병경기를 개설하고, 개인 용병들이 실력·매너 정보를 기반으로 신청·참여하는 **사회인야구 용병경기 전용 플랫폼**이다.

핵심 차별점은 두 가지다.

1. **주최자 수수료 영구 0원** — 네이버 밴드 대비 전환 비용을 제거한다.
2. **평판 커뮤니티 레이어** (선수 카드, 상호 평가, 노쇼 이력) — 매치매치가 해결하지 못한 신뢰 문제를 구조적으로 해결한다.

매치매치가 6년간 시장 장악에 실패하면서 생긴 공백을 노린다.

## 2. Background & Context

### 현재 문제

사회인야구 용병경기 모집은 네이버 밴드, 다음카페, 게임원 게시판 등에 분산되어 있다.

- **용병 입장**: 여러 커뮤니티를 가입해 경기를 찾아다녀야 하고, 포지션 중복이나 수준 미스매치가 잦다.
- **주최자 입장**: 댓글·쪽지로 신청자를 수동 관리하고, 노쇼 발생 시 제재 수단이 없다.

### 경쟁 환경

| 플레이어    | 포지션                        | 약점                                                                                 |
| ----------- | ----------------------------- | ------------------------------------------------------------------------------------ |
| 네이버 밴드 | 실질적 최대 경쟁자. 무료·친숙 | 리그별 분산, 검색/필터 부재, 평판 축적 불가                                          |
| 매치매치    | 유일한 전용 앱, 2019년 출시   | iOS 리뷰 16건·3.8점. 리그에 수수료 10% 부과, 기술 불안정, 밴드 대비 차별화 가치 부족 |
| 게임원      | 사회인야구 기록 포털          | 용병 매칭은 부가 기능 수준. 포지션 선택·신청 관리 없음                               |

### 매치매치 실패 원인 (구조적 분석)

- **양면시장 수수료 딜레마**: 주최자·용병 어느 쪽도 수수료를 내지 않으려 밴드로 이탈
- **낮은 거래 단가**: 참가비 2~4만 원의 10% = 2~4천 원. 운영비 대비 수익 불가
- **평판 시스템 부재**: 노쇼 해결책은 결제가 아닌 사회적 평판인데 이를 구축하지 못함

### 법적 고려

- 결제 시스템을 붙이지 않고 **계좌이체 직접 송금** 방식을 유지해 플랫폼은 정보 중개자로 남는다. 이를 통해 전자금융거래법·통신판매업 신고 대상에서 벗어나는 것을 목표로 한다. (→ 법률 검토 필요 여부는 [Open Questions](#10-open-questions) 참고)
- 입금자명, 주최자 계좌번호, 알림톡 수신용 휴대폰 번호, 노쇼·평가 이력 등 **개인정보를 처리**하므로 개인정보 처리방침·이용약관이 베타 오픈 전에 필요하다.
- 환불은 주최자–용병 간 직접 처리이며, 플랫폼은 환불 책임을 지지 않는다는 점을 약관에 명시한다.

## 3. Objectives & Success Metrics

### Goals

MVP 출시 후 3개월 내 아래 3개 가설을 검증한다.

1. 주최자가 수수료 0원 조건에 매력을 느끼고 경기를 지속 개설하는가
2. 용병이 밴드 대신 이 플랫폼을 선택할 충분한 가치가 있는가
3. 실력 기반 매칭이 경기 품질을 실제로 개선하는가

### Non-Goals (MVP 제외)

- 결제 연동 (PG사 연동)
- 팔로우·피드 시스템
- 게임원 공식 API 연동
- iOS·Android 네이티브 앱
- 채팅·DM (MVP 이후 운영 데이터를 보고 도입 판단, D13)
- 게이미피케이션 (배지, 랭킹)

> v1에서 Non-Goals에 있던 "대기열 자동 승격"은 P1-2와 충돌하여 Non-Goals에서 제거하고 P1로 유지한다.

### Success Metrics

| 지표                  | 현재 | 목표 (3개월)                  | 측정 방법                        |
| --------------------- | ---- | ----------------------------- | -------------------------------- |
| 주 단위 경기 개설 수  | 0    | 주최자 5명 이상이 주 1회 이상 | DB 집계                          |
| 경기 예약률           | —    | 정원 대비 70% 이상            | 예약 수 / 정원                   |
| 입금 완료 전환율      | —    | 80% 이상 (24시간 내)          | `PAYMENT_SUBMITTED` / `RESERVED` |
| 관리자 승인 평균 시간 | —    | 4시간 이내                    | 상태 전이 타임스탬프             |

### 실패 신호

- 주최자가 한두 번 올리고 중단
- 예약은 많지만 입금 전환율 낮음 (신뢰 부족 또는 UX 문제)
- 재방문율 10% 이하 (1회성 서비스로 소비됨)

> 실패 신호 발생 시 기능 추가가 아닌 **가설 재검토**로 대응한다.

## 4. Target Users & Segments

### 공급자 (주최자)

- **구장 운영자**: 정기적으로 용병경기를 개설, 다수의 모집 채널 운영 부담
- **리그 운영자**: 시즌 외 친선경기 또는 빈 팀 자리 채우기 필요
- **팀장**: 소속 팀 경기에 추가 용병 필요 시 모집

현재 워크플로우: 네이버 밴드에 모집글 → 댓글로 신청자 관리 → 문자/입금 확인 수동 처리

### 수요자 (용병)

- **핵심 타깃**: 30~50대 남성, 소속 팀 외 추가 경기를 원하는 사회인야구 플레이어
- **행동 특성**: 여러 밴드 가입, 원하는 포지션·수준의 경기 탐색에 시간 소요
- **페인포인트**: 수준 미스매치, 노쇼로 인한 경기 불성립, 신뢰할 수 있는 평판 정보 부재

### 관리자 (운영자)

- 신고 처리, 노쇼·평가 이의제기 처리, 노쇼 2회 도달 계정 검토, 계정 정지, 리그·구장 데이터 관리

### 초기 집중 지역

- 전국 오픈 금지. **1개 지역 포화 전략** (직접 방문 가능, 구장·리그 밀집, 개인 네트워크 존재 도시)
- **경기도 내 인접 시 2~4곳**으로 시작한다. 구체적인 시는 0단계(지역 확정 작업)에서 확정한다.
- 초기 목표: 주최자 5~10곳, 용병 50~100명

| 브라우저      | 최신 Chrome·Safari·삼성 인터넷, **카카오톡 인앱 브라우저** (알림톡 링크 진입 경로)                   |
| 시간          | 모든 시각은 KST 기준으로 표시·계산. DB는 `timestamptz` 저장                                          |
| 동시성        | 잔여 1자리 동시 예약 시 1명만 성공 (P0-3). 동시성 테스트로 검증                                      |
| 보안·개인정보 | 계좌번호·휴대폰 번호는 응답 DTO에서 필요한 화면에만 노출. 노쇼 상세 이력은 관리자만 열람. HTTPS 필수 |
| 가용성        | API 단일 인스턴스 (Cron 전제). 장애 시 수동 재기동 허용 (MVP)                                        |

> 예약·취소·노쇼·평가 등 세부 운영 규칙은 [정책 명세서](policy.md)에서 관리한다. PRD와 충돌 시 PRD가 우선하며, 정책 명세서에서 확정된 항목 중 PRD 범위 변경이 필요한 것은 Decision Log에 반영한다.

## 6. Solution Overview

### 핵심 설계 원칙

> **"주최자에겐 무료, 용병에겐 커뮤니티."** — 매치매치가 실패한 수수료 구조를 구조적으로 뒤집는다.

### 예약·승인 플로우

```
[용병] 포지션 예약 (입금자명 입력 필수)
  ↓  RESERVED / 포지션 잠금
[용병] 24시간 내 계좌이체 + "입금 완료" 버튼
  ↓  PAYMENT_SUBMITTED
[주최자] 은행 앱 대조 후 "승인" 버튼
  ↓  APPROVED → 참가 확정 알림
[경기 후]
  → ATTENDED 또는 NO_SHOW 표시
  → 상호 평가 화면 노출
```

### 상태 모델

```
RESERVED ─┬─> PAYMENT_SUBMITTED ─┬─> APPROVED ─┬─> ATTENDED
          │                      │             ├─> NO_SHOW
          │                      │             └─> CANCELLED (경기 24시간 전까지)
          │                      ├─> REJECTED
          │                      ├─> EXPIRED   (경기 시작 시점까지 미승인)
          │                      └─> CANCELLED (사용자 취소)
          ├─> EXPIRED   (예약 후 24시간 내 입금 체크 없음)
          └─> CANCELLED (사용자 취소)

* 경기 취소 시: 모든 활성 상태(RESERVED / PAYMENT_SUBMITTED / APPROVED) ─> GAME_CANCELLED
```

| 상태                | 설명                                                                                        | 포지션 |
| ------------------- | ------------------------------------------------------------------------------------------- | ------ |
| `RESERVED`          | 예약됨, 입금 대기 중                                                                        | 잠김   |
| `PAYMENT_SUBMITTED` | 사용자 입금 완료 체크, 주최자 확인 대기. 4시간 미처리 시 주최자 리마인드                    | 잠김   |
| `APPROVED`          | 승인 완료, 참가 확정                                                                        | 잠김   |
| `EXPIRED`           | ① 예약 후 24시간 내 입금 체크 없음 ② 경기 시작 시점까지 주최자 미승인 — 자동 취소           | 재오픈 |
| `CANCELLED`         | 사용자 직접 취소 (`RESERVED`/`PAYMENT_SUBMITTED`는 언제든, `APPROVED`는 경기 24시간 전까지) | 재오픈 |
| `REJECTED`          | 주최자가 입금 불일치 등으로 거절                                                            | 재오픈 |
| `GAME_CANCELLED`    | 주최자가 경기 자체를 취소 (경기 시작 전 언제든, 사유 필수)                                  | —      |
| `ATTENDED`          | 참가 완료                                                                                   | —      |
| `NO_SHOW`           | 경기 후 주최자가 노쇼 표시. 노쇼 정책(D12, D14) 적용                                        | —      |

- 상태 전이는 서버(`apps/api`)의 단일 도메인 서비스에서만 수행하고, 허용되지 않은 전이는 예외로 거부한다.
- 상태 enum은 `packages/shared`에 정의해 프론트/백엔드가 동일한 값을 사용한다.

### 실력 기반 매칭

- 주최자가 급수 필터 설정 (예: "4부 이하만 신청 가능")
- 용병은 선수 카드에 게임원·유니크플레이 프로필 URL 수동 연동
- 경기 후 "실력이 프로필과 일치했나" 평가로 데이터 정제
- 선수 카드에 **외부 프로필 연동 여부를 표시**해 연동 유인 제공 (배지 시스템은 Non-Goal)

### 평가 시스템

- **카테고리**: 매너, 실력-프로필 일치도, 시간 준수 (각 1~5점)
- **베스트플레이어 투표**: 1명 선택 (점수 인플레이션 방지용 상대평가)
- **평가 대상**: 같은 경기의 `ATTENDED` 참가자 간 (주최자 포함 여부는 Open Question)
- **신고 플로우**: 매너 이슈는 평가와 분리된 별도 신고로 처리 → 관리자 검토 (P0-13)

## 7. Technical Architecture

### 7.1 모노레포 구조

pnpm workspaces + Turborepo 기반 모노레포로 프론트엔드와 백엔드를 하나의 저장소에서 관리한다.

```
yaguhae/
├─ apps/
│  ├─ web/            # Next.js (App Router)
│  └─ api/            # NestJS (+ TypeORM Entity, Migration)
├─ packages/
│  ├─ shared/         # 상태 enum, 상수, 검증 스키마, 공용 타입 (런타임 의존성 최소)
│  ├─ api-client/     # OpenAPI 스펙 기반 생성 클라이언트 (orval)
│  ├─ eslint-config/
│  └─ tsconfig/
├─ turbo.json
└─ pnpm-workspace.yaml
```

**패키지 경계 원칙**

- TypeORM Entity 클래스는 `apps/api` 내부에만 둔다. `packages/shared`에는 데코레이터나 `reflect-metadata`에 의존하지 않는 순수 타입·enum·상수만 둔다. (Entity가 web 번들에 섞이는 것을 방지)
- `apps/web`은 `packages/api-client`를 통해서만 API를 호출한다.

### 7.2 기술 스택

| 역할              | 선택                                                       | 비고                                                                                                                                                 |
| ----------------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 모노레포          | pnpm workspaces + Turborepo                                | 빌드 캐시, `turbo prune`으로 앱별 Docker 빌드                                                                                                        |
| 백엔드 프레임워크 | NestJS (`apps/api`)                                        | 모듈 구조, DI, 데코레이터 기반                                                                                                                       |

| 트랜잭션          | `typeorm-transactional`                                    | 서비스 메서드에 `@Transactional()` 선언. 앱 부트스트랩 전 `initializeTransactionalContext()`, DataSource 생성 시 `addTransactionalDataSource()` 등록 |

| 실시간            | MVP는 폴링, 이후 Socket.io (NestJS Gateway) 검토           | 잔여 자리 시각화                                                                                                                                     |
| 알림              | 카카오 알림톡 (D11)                                        | 사업자 등록·비즈니스 채널 개설·발송 대행사 선정·템플릿 사전 심사 필요. 3단계(12주차) 전 템플릿 승인 완료 목표                                        |

| 배포 (백엔드)     | AWS EC2 + Docker                                           | `api.<도메인>`. `turbo prune api --docker`로 이미지 빌드                                                                                             |

### 7.3 데이터·동시성 원칙

- **스키마 변경은 마이그레이션으로만** 한다. 모든 환경에서 `synchronize: false`. 마이그레이션은 CI/CD 배포 단계에서 앱 교체 전에 자동 실행한다. 스테이징이 없으므로 마이그레이션은 하위 호환(컬럼 추가 → 배포 → 이후 정리) 방식으로 작성한다.
- **동시 예약 경쟁** (잔여 1자리에 동시 예약): 예약 트랜잭션 안에서 포지션 슬롯 row에 비관적 락(`pessimistic_write`)을 건다. `(game_id, user_id)` 활성 예약 unique 제약을 이중 안전장치로 둔다.
- **트랜잭션은 `typeorm-transactional`로 통일**한다. 서비스 메서드에 `@Transactional()`을 선언하고, Repository는 트랜잭션 컨텍스트를 자동으로 따른다. 동시성 테스트로 락·롤백 동작을 검증한다.
- **응답은 DTO로 매핑**한다. Entity를 그대로 반환하지 않는다. 계좌번호, 노쇼 상세 등 민감 필드 노출을 막고, 이 DTO가 OpenAPI 스키마의 기준이 된다.
- 만료 Cron은 조건부 업데이트로 사용자 액션과의 경합에 안전하게 처리한다.
  - `WHERE status = 'RESERVED' AND reserved_at < now() - interval '24 hours'`
  - `WHERE status = 'PAYMENT_SUBMITTED' AND game.starts_at <= now()`
- **지역·리그·구장 데이터**: 지역은 시/군/구 표준 코드 테이블로 관리한다. 리그는 구장(경기장)을 구분하는 단위로, 해당 구장이 기존에 어떤 리그에서 쓰이는지와 매칭된다. 구장은 리그 하나에만 소속된다(리그 1 : 구장 N). 관리자가 초기 지역의 리그·구장을 시드 데이터로 등록하고, 주최자의 신규 구장 등록 요청은 관리자 승인 후 노출한다.

**DB 호스팅 (Supabase) 운영 주의**

- 무료 플랜은 일정 기간 비활성 시 프로젝트가 일시정지되므로, 베타 오픈 전 Pro 플랜 전환 또는 비활성 방지 대책을 마련한다.
- Supabase Direct connection은 IPv6 전용이므로 EC2(IPv4)에서는 **Session pooler**(5432) 접속 문자열을 사용한다. 장기 실행 서버에서는 Transaction pooler(6543)를 쓰지 않는다.
- 마이그레이션도 같은 접속 문자열로 실행하며, DB 비밀번호·URL은 GitHub Actions Secrets와 EC2 환경변수로만 관리한다.

### 7.4 인증·도메인 구성

- 커스텀 도메인을 구매해 **서브도메인으로 분리**한다.
  - 프론트: `app.<도메인>` (Vercel)
  - 백엔드: `api.<도메인>` (EC2, HTTPS 인증서 적용)
- refresh 토큰 쿠키: `HttpOnly; Secure; SameSite=Lax; Domain=.<도메인>`
- 카카오 OAuth Redirect URI는 `api.<도메인>`의 콜백 엔드포인트로 등록한다.
- CORS 허용 origin은 `app.<도메인>`과 Vercel Preview 도메인으로 제한한다. 환경변수(카카오 키, JWT 시크릿, DB URL)는 앱별로 분리 관리한다.
- Vercel Preview 도메인은 상위 도메인이 달라 refresh 쿠키가 공유되지 않으므로, Preview에서는 로그인 플로우 검증을 하지 않거나 별도 테스트 로그인을 둔다.

### 7.5 아키텍처 결정 배경 (v1 → v2)

| 영역      | v1 (Supabase)       | v2 (NestJS + Next.js 모노레포)                                               |
| --------- | ------------------- | ---------------------------------------------------------------------------- |
| 인증/인가 | Supabase Auth + RLS | Passport/JWT + Guard. DB가 강제하던 권한을 애플리케이션 레이어에서 직접 체크 |
| 자동 만료 | pg_cron             | `@nestjs/schedule` Cron Job                                                  |
| 실시간    | Supabase Realtime   | 폴링 → Socket.io Gateway 검토                                                |
| 배포      | 단일 플랫폼         | 프론트/백엔드 별도 배포, CORS·환경변수 관리 필요                             |
| 코드 관리 | —                   | 모노레포로 타입·상수 공유, API 계약 자동 생성                                |

**트레이드오프**

- **개발 기간**: 토대 단계 2~3주 → 4~6주로 증가. 개발 전체 14~16주 → 약 19주.
- **포트폴리오 가치**: JWT 리프레시 전략, Guard 기반 권한 체계, TypeORM 트랜잭션 + 비관적 락 기반 동시성 처리, 모노레포 타입 공유·계약 기반 개발을 직접 구현한 코드로 보여줄 수 있다.
- **우선순위**: 카카오 OAuth 콜백, 알림톡 발송 연동, 파일 업로드 같은 배관성 작업은 라이브러리·예제 코드로 최소화한다. 상태머신·동시성·권한 체계에 시간을 투자한다.

### 1단계: 토대 (1~6주차)

- 모노레포 세팅 (pnpm + Turborepo, 공용 tsconfig/eslint, `packages/shared`)

- Supabase 프로젝트(서울 리전) 생성, Session pooler 연결
- ERD 최종안 확정, TypeORM Entity 정의 및 초기 마이그레이션, CI/CD 자동 마이그레이션

- 시군구 코드·초기 지역 리그·구장 시드 데이터

- Swagger → orval 클라이언트 생성 파이프라인
- 선수 카드 프로필 CRUD

### 2단계: 핵심 거래 플로우 (7~11주차)

- 경기 개설·조회·필터(리그별 탐색 포함)·예약
- 예약 동시성 처리 (비관적 락 + unique 제약) 및 동시성 테스트
- 입금자명 입력, 입금 완료 체크 UI
- 주최자 대시보드 (신청 상태 관리, 승인/거절, 경기 취소·사유 입력)
- 용병 예약 취소 (승인 후 경기 24시간 전까지)
- 자동 만료 처리 (`@nestjs/schedule`): 입금 24시간 만료, 경기 시작 시 미승인 건 만료
- 0단계에서 확보한 주최자 5명에게 테스트 의뢰

### 3단계: 평가·노쇼·알림·관리자 (12~15주차)

- 경기 후 상호 평가 UI (매너·실력·시간준수 + 베스트플레이어)

- 카카오 알림톡 발송 (만료 12h/1h 전, 승인 완료·거절, 새 입금 건, 승인 방치 리마인드, 예약·경기 취소)

- 개인정보 처리방침·이용약관 게시

### 베타 오픈 조건

아래를 모두 충족해야 4단계(실사용자 투입)를 시작한다.

### 채팅 (MVP 이후 도입 시 설계 방향)
